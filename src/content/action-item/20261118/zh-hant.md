# 夜間 AI 的兩座時鐘

有些工作即使要等上幾個小時才得到答案，仍然有價值。為第二天早晨準備報告、提出軟體修復方案，或審閱一份長文件，都容得下等待。對將 AI 整合到軟體中的人來說，這種時間彈性帶來一個經濟問題：如果服務有更多時間作答，這項工作的成本能降低多少？

開發 GPT 系列 AI 模型的 OpenAI，如今提供了一種具體方式來進行這種權衡。它的後臺處理選項允許模型請求使用更長的完成時間視窗，換取更低的模型 token 費率。八小時視窗聽起來尤其適合夜間工作：晚上提交任務，早晨領取結果。

但要弄清“結果”指什麼，還需要仔細看一看。AI 響應可以是一份完成的答案，也可以是要求獲取資訊的請求；周邊軟體必須先取回這些資訊，工作才能繼續。兩者都算響應，但整個任務所處的階段並不相同。

這一區別很重要，因為夜間 AI 涉及兩隻相關的時鐘。一隻衡量模型響應何時到達，另一隻衡量有用且完整的成果何時到達。

OpenAI 於 2026 年 11 月 17 日釋出的兩個新模型，為這個問題增添了新的選擇。GPT-6.2 Sol 是其面向日常程式設計和智慧體工作流程的高效模型。智慧體工作流程指的是軟體藉助 AI 模型執行任務的一系列步驟。GPT-6.2 Astra 則是其面向高難度推理和程式設計任務、價格更高的前沿模型。

應用程式透過 API 使用這些模型。API 是一個結構化的入口，讓一個程式能夠請求另一項服務完成工作。開發者可以使用 OpenAI 的 Responses API 向模型傳送指令、獲取回答，並處理模型提出的工具使用請求。例如，某個工具可能用於查詢文件。應用程式執行查詢，再把找到的資訊交還給模型。

Responses API 還支援後臺模式。請求可以持續執行，應用程式則檢查進度，稍後再取回響應。這樣，應用程式就能管理需要等待一段時間才能得到回答的工作。

對初次接觸這些系統的讀者來說，理解這種分工很重要。模型生成響應。應用程式管理更長的工作過程：提供資訊、執行工具、發出後續請求、檢查結果並交付完成的工作。整套安排是否有用，取決於這些環節如何協同。

價格說明了運營者為何會關注等待時間。OpenAI 按 token 收費；token 是模型處理或生成的文字小單元。輸入 token 對應傳送給模型的內容，輸出 token 對應模型生成的內容。

對於較短的請求，按 Standard 費率計算，Sol 每百萬輸入 token 收費 2 美元，每百萬輸出 token 收費 10 美元。Astra 對應的價格分別為 8 美元和 40 美元，均為 Sol 對應費率的四倍。輸入 token 超過 272,000 的請求適用更高的價格檔位：輸入和快取輸入費率翻倍，輸出費率則提高到較短請求費率的 1.5 倍；這些費率適用於整個請求。

這些是起始價格。OpenAI 的後臺模式文件介紹了兩種目前處於公開測試階段的完成時間視窗：兩小時和八小時。兩小時選項的模型 token 費率比 Standard 低 30%；八小時選項低 40%。

延遲成了定價因素。日程靈活的運營者可以接受更長的響應視窗，以較低費率使用模型。文件明確說明的收益是價格下降；更長的視窗會對答案質量產生什麼影響，仍是一個有待實證回答的問題。

關於時間的措辭同樣值得留意。OpenAI 表示，API 以在所選視窗內完成**初始響應**為目標，計時從它接受請求時開始。這針對的是某一次特定響應。由應用程式管理的完整任務則有更長的時間線。

OpenAI 文件中的例子清楚地說明了這一區別。應用程式傳送一個完成時間視窗為八小時的請求。模型的第一次響應要求應用程式查詢一份文件。應用程式完成查詢，然後在後續請求中提交取回的資訊。

此時，第一次響應已經到達，但更大的任務仍在繼續。應用程式還要管理後續的一切：進一步互動、檢查、問題恢復和最終交付。如果應用程式複用完成時間視窗、續接 ID、模型和專案，符合條件的後續請求也可以享受折扣。這些條件使工作過程繼續時仍符合折扣資格；初始響應目標的適用範圍則仍然明確。

可以想象一家夜間營業的麵包房承諾，第一盤烘焙食品會在早晨出爐。要把一份完整的早餐送到家，還需要打包食物、安排司機、核對地址，並在道路封閉時尋找其他路線。

在這個比喻中，第一盤出爐的食品是模型響應。早餐送達正確地址，才是完成的工作流程。第一盤何時出爐會影響配送，而配送還依賴後續多個環節。即使第一盤準時出爐，接下來的路程仍可能困難重重。

同樣的區別賦予了八小時 AI 視窗實際意義。如果初始響應包含完整答案，應用程式可能已接近交付。如果響應要求提供文件，就需要開啟下一輪互動。核驗可能帶來修改，工具呼叫失敗可能需要恢復。協調這些工作是應用程式的責任；文件規定的視窗提供的是響應時間目標，而非端到端的交付保證。

這也改變了折扣的解讀方式。模型 token 費率降低 40%，意味著賬單中的一個組成部分變便宜了。但產出有用結果的成本還可能包括工具費用、重複請求、重試、應用程式的計算開銷和人工審閱。失敗的嘗試也會消耗資源。

因此，Astra 較高的 token 價格和 Sol 較低的 token 價格，確定的是按所述費率購買模型輸出的成本。哪個模型能以更低成本產出成功交付的成果，取決於完整任務。OpenAI 的基準測試對比和早期測試者的說法，是在各自所述條件下由提供方給出的證據。要衡量某個具體應用程式的交付成本，還需要該應用程式自身的資料。

對 RobinOS 來說，針對這些新後臺時間視窗的受控比較仍是未來的工作。每份成功交付成果的成本、人工介入時間、故障恢復負擔，以及能夠有效無人值守執行的時長，都有待測量。

有意義的比較應固定一項真實任務，分別用 Sol 和 Astra 執行，並持續追蹤到成功交付。重要的觀測結果包括總成本、人工協助所花的分鐘數，以及工作過程中的某個環節失敗時會發生什麼。這才能把模型價格和響應時間與運營者的實際目標聯絡起來。

11 月 17 日的釋出帶來了新的模型選擇，後臺時間視窗則提供了響應時間與 token 費率之間的明確交換。夜間工作的更大價值，取決於從請求被接受到成果交付完成的整個過程。

在判斷 AI 能否有效自主工作時，運營者該看哪隻時鐘：在模型第一次響應時停下的那隻，還是在工作成功交付時才停下的那隻？
