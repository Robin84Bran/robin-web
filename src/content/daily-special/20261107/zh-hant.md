# AI Agent 如何記住已經完成的工作

AI Agent 能做的事情，已經超出生成一段回答。它可以調用工具查資料、做計算或執行操作，再根據返回結果決定下一步。軟件因此能夠把一項任務分成多個步驟向前推進，也會遇到一個熟悉的電腦問題：進程可能在半路崩潰。

Mistral AI 開發 AI 模型，也營運一套名為 Studio 的開發平台。對它來說，處理中斷屬於模型外圍基礎設施的一部分。2026 年 11 月 5 日，Mistral 宣布 Managed Agents 進入公開預覽。同期的 Studio 發布把 Agent、工作流程、應用程式，以及觀察和評估這些系統的工具放到同一個平台裏。

恢復承諾很直接。Mistral 表示，部署後的 Agent 進程崩潰時，可以從最後一個已經完成的模型調用或工具調用繼續。理解這項能力，首先要分清兩樣東西：正在工作的軟件，與記錄哪些工作已經完成的帳本。

一個小型本地實驗把這一區別變得具體。它還帶出第二個問題：當 Agent 的工具改變了外部世界，究竟哪一本帳能告訴我們事情真的發生了甚麼？

## 工作者與它的記憶

Mistral 把 Agent 描述為模型加上一個 *harness*，也就是運行框架。模型決定下一步做甚麼；運行框架管理模型回覆、工具調用和工具結果之間的循環。*session*，即會話，則保存訊息、工具調用和工具返回結果等活動記錄。

*worker* 是此刻實際執行工作的進程。在已部署的 Studio 架構裏，會話記錄與單個 worker 分開保存。發生中斷後，替代進程便有一份可以查閱的記錄。

可以把檢查點想成夾在讀完那一頁之後的書籤。讀者合上書，過一會兒再打開，書籤會把人帶到下一頁。Agent 的檢查點作用相似：它標記已經完成的步驟，讓處理過程從那裏繼續向前。

書籤放在哪裏很關鍵。「準備調用工具」與「工具已經返回結果」描述的是兩個相隔一步的位置。Mistral 的概覽寫明，恢復點位於最後一個*已經完成*的模型調用或工具調用之後。

Managed Agents 和 Agents SDK 目前處於公開預覽。Mistral 表示，這一階段的介面、行為和限制都可能變化。平台恢復能力屬於公司的公開說明；下面的本地實驗規模小得多，只觀察同一種檢查點機制。

## 一次計算與一次主動中斷

這項受控測試使用一個確定性的 Python 運行框架，也就是每次都按照固定次序執行。整個任務從一段本地字串開始：

`managed-agent-recovery-2026-11-07`

唯一的工具計算這段字串的 SHA-256 摘要。SHA-256 會把輸入變成固定長度的數碼指紋；相同輸入會得到相同結果。這個特性提供了一個可預測的答案，方便運行框架重啟後核對。

全部工作都留在本機。工具只使用處理器時間，外部副作用計數為零。這樣，實驗可以專注觀察進度如何保存與恢復。

第一個進程算出摘要，並把結果與名為 `after:sha256-local-string` 的檢查點一起保存。這次保存採用原子寫入，結果和檢查點作為一次完整更新落盤。隨後，進程主動以退出碼 75 結束，保存狀態為 `INTERRUPTED_AFTER_COMPLETED_TOOL`。

這段次序正是實驗核心。計算已經完成，結果已經寫入，然後執行停止。

第二次啟動讀取檢查點，核對保存的摘要，從完成後的工具步驟繼續。它生成最終結果，並以原子寫入保存 `COMPLETE` 狀態。最後一條訊息是：「Recovered from the completed tool checkpoint.」——系統從已完成工具的檢查點恢復。

兩次啟動合計只執行了一次工具。重複工具操作為零。

書籤發揮了作用。第二個進程找到足夠的持久資訊——第一進程結束後依然存在的資訊——然後越過已經完成的計算繼續工作。

這份證據只覆蓋一個運行框架、一次運行和一個經過選擇的中斷位置。研究全部在本地進行，使用本地計算和本地狀態。Mistral 的託管運行環境、網絡故障期間的恢復、多個 worker 重疊執行，以及保存記錄受損時的表現，都屬於另外的測試範圍。

這個狹窄結果仍然有價值：在中斷前寫下完成記錄，使本次運行框架恢復時能夠跳過已經完成的唯讀工具步驟。

## 當工具伸向外部世界

本地計算給運行框架留下的題目相對簡單。答案保存以後，下一個進程可以直接讀取。

外部操作會引入另一個參與者，也帶來另一本帳。想像一個 Agent 請速遞服務寄出包裹。速遞系統可能已經接受請求，而確認訊息在返回途中丟失。此時，Agent 手上的回執停留在請求發出，速遞服務則可能已經開始運送。

Agent 的書籤與速遞服務的記錄分別描述同一事件的兩個部分。前者記錄 Agent 走到哪裏；後者記錄寄件請求的受理狀態。

Mistral 的工具文件專門解釋了這道邊界。文件稱，部署後的單次工具調用最多執行一次。同時，它也描述了一種「調用回執丟失」的狀態：模型獲知這次調用可能已經生效，或效果仍待確認。

兩句話回答的是兩個問題。第一句關注某一次工具調用的執行次數；第二句關注系統掌握外部效果的程度。執行次數受到限制，結果認知仍可能留有空白。

模型決定下一步時，這道資訊空白會產生影響。後續請求可能再次提出同一個外部操作。因此，Mistral 建議讓改變外部系統的工具具備安全重試能力，首選方式是使用*冪等鍵*。

冪等鍵是一項請求攜帶的穩定標識。在寄包裹的例子裏，它像一張始終對應同一票貨物的運單號。服務再次收到帶有同一標識的請求時，可以識別原操作，把重複請求當成同一件工作處理。

外部服務需要支援這種行為，冪等鍵才能提供保護。對於透過其他方式可以查詢操作狀態的服務，Mistral 建議先查再重試。唯讀工具每次執行都保持外部系統原狀，因此可以省去這項標識。

本地實驗展示了故事裏「書籤」這一半。保存下來的完成記錄，讓一次已完成計算跨過中斷繼續存在。寄包裹、轉帳或發布頁面的工具還需要另一半：把重複請求與原來的外部操作連接起來。

持久化的 Agent 會話可以回答：「處理過程應該從哪裏繼續？」安全的外部操作還要回答：「接收方已經做了甚麼？」Agent 獲得愈來愈多實用工具之後，可靠恢復取決於這兩個答案能否始終連在一起。
