# AI Agent 如何记住已经完成的工作

AI Agent 能做的事情，已经超出生成一段回答。它可以调用工具查资料、做计算或执行操作，再根据返回结果决定下一步。软件因此能够把一项任务分成多个步骤向前推进，也会遇到一个熟悉的计算机问题：进程可能在半路崩溃。

Mistral AI 开发 AI 模型，也运营一套名为 Studio 的开发平台。对它来说，处理中断属于模型外围基础设施的一部分。2026 年 11 月 5 日，Mistral 宣布 Managed Agents 进入公开预览。同期的 Studio 发布把 Agent、工作流、应用，以及观察和评估这些系统的工具放到同一个平台里。

恢复承诺很直接。Mistral 表示，部署后的 Agent 进程崩溃时，可以从最后一个已经完成的模型调用或工具调用继续。理解这项能力，首先要分清两样东西：正在干活的软件，与记录哪些工作已经完成的账本。

一个小型本地实验把这一区别变得具体。它还带出第二个问题：当 Agent 的工具改变了外部世界，究竟哪一本账能告诉我们事情真的发生了什么？

## 工作者与它的记忆

Mistral 把 Agent 描述为模型加上一个 *harness*，也就是运行框架。模型决定下一步做什么；运行框架管理模型回复、工具调用和工具结果之间的循环。*session*，即会话，则保存消息、工具调用和工具返回结果等活动记录。

*worker* 是此刻实际执行工作的进程。在已部署的 Studio 架构里，会话记录与单个 worker 分开保存。发生中断后，替代进程便有一份可以查阅的记录。

可以把检查点想成夹在读完那一页之后的书签。读者合上书，过一会儿再打开，书签会把人带到下一页。Agent 的检查点作用相似：它标记已经完成的步骤，让处理过程从那里继续向前。

书签放在哪里很关键。“准备调用工具”与“工具已经返回结果”描述的是两个相隔一步的位置。Mistral 的概览写明，恢复点位于最后一个*已经完成*的模型调用或工具调用之后。

Managed Agents 和 Agents SDK 目前处于公开预览。Mistral 表示，这一阶段的接口、行为和限制都可能变化。平台恢复能力属于公司的公开说明；下面的本地实验规模小得多，只观察同一种检查点机制。

## 一次计算与一次主动中断

这项受控测试使用一个确定性的 Python 运行框架，也就是每次都按照固定顺序执行。整个任务从一段本地字符串开始：

`managed-agent-recovery-2026-11-07`

唯一的工具计算这段字符串的 SHA-256 摘要。SHA-256 会把输入变成固定长度的数字指纹；相同输入会得到相同结果。这个特性提供了一个可预测的答案，方便运行框架重启后核对。

全部工作都留在本机。工具只使用处理器时间，外部副作用计数为零。这样，实验可以专注观察进度如何保存与恢复。

第一个进程算出摘要，并把结果与名为 `after:sha256-local-string` 的检查点一起保存。这次保存采用原子写入，结果和检查点作为一次完整更新落盘。随后，进程主动以退出码 75 结束，保存状态为 `INTERRUPTED_AFTER_COMPLETED_TOOL`。

这段顺序正是实验核心。计算已经完成，结果已经写入，然后执行停止。

第二次启动读取检查点，核对保存的摘要，从完成后的工具步骤继续。它生成最终结果，并以原子写入保存 `COMPLETE` 状态。最后一条消息是：“Recovered from the completed tool checkpoint.”——系统从已完成工具的检查点恢复。

两次启动合计只执行了一次工具。重复工具操作为零。

书签发挥了作用。第二个进程找到足够的持久信息——第一进程结束后依然存在的信息——然后越过已经完成的计算继续工作。

这份证据只覆盖一个运行框架、一次运行和一个经过选择的中断位置。研究全部在本地进行，使用本地计算和本地状态。Mistral 的托管运行环境、网络故障期间的恢复、多个 worker 重叠执行，以及保存记录受损时的表现，都属于另外的测试范围。

这个狭窄结果仍然有价值：在中断前写下完成记录，使本次运行框架恢复时能够跳过已经完成的只读工具步骤。

## 当工具伸向外部世界

本地计算给运行框架留下的题目相对简单。答案保存以后，下一个进程可以直接读取。

外部操作会引入另一个参与者，也带来另一本账。想象一个 Agent 请快递服务寄出包裹。快递系统可能已经接受请求，而确认信息在返回途中丢失。此时，Agent 手上的回执停留在请求发出，快递服务则可能已经开始运送。

Agent 的书签与快递服务的记录分别描述同一事件的两个部分。前者记录 Agent 走到哪里；后者记录寄件请求的受理状态。

Mistral 的工具文档专门解释了这道边界。文档称，部署后的单次工具调用最多执行一次。同时，它也描述了一种“调用回执丢失”的状态：模型获知这次调用可能已经生效，或效果仍待确认。

两句话回答的是两个问题。第一句关注某一次工具调用的执行次数；第二句关注系统掌握外部效果的程度。执行次数受到限制，结果认知仍可能留有空白。

模型决定下一步时，这道信息空白会产生影响。后续请求可能再次提出同一个外部操作。因此，Mistral 建议让改变外部系统的工具具备安全重试能力，首选方式是使用*幂等键*。

幂等键是一项请求携带的稳定标识。在寄包裹的例子里，它像一张始终对应同一票货物的运单号。服务再次收到带有同一标识的请求时，可以识别原操作，把重复请求当成同一件工作处理。

外部服务需要支持这种行为，幂等键才能提供保护。对于通过其他方式可以查询操作状态的服务，Mistral 建议先查再重试。只读工具每次执行都保持外部系统原状，因此可以省去这项标识。

本地实验展示了故事里的“书签”这一半。保存下来的完成记录，让一次已完成计算跨过中断继续存在。寄包裹、转账或发布页面的工具还需要另一半：把重复请求与原来的外部操作连接起来。

持久化的 Agent 会话可以回答：“处理过程应该从哪里继续？”安全的外部操作还要回答：“接收方已经做了什么？”Agent 获得越来越多实用工具之后，可靠恢复取决于这两个答案能否始终连在一起。
