# Claude 的暫存記憶過期後會發生甚麼事

與 AI 助手對話時，交流看起來是連續的。你提出問題、讀完回答，再補充一個細節。支撐這段交流的軟件必須把足夠的前文交給模型，它才能理解每一條新訊息。在一般做法中，對話愈長，應用程式就愈需要重複傳送較早的訊息。

重複傳送這些內容，是智能體應用程式承擔的工作之一。應用程式位於用戶與模型之間：它收集訊息、保存對話紀錄並準備請求。使用工具的應用程式還可能安排查詢資料、修改紀錄等動作。Anthropic 的 AI 模型 Claude 則根據應用程式提供的上下文生成回答。

2026 年 11 月 2 日，Anthropic 宣布推出一項名為 **Message Threads** 的測試功能，改變了應用程式傳送上下文的方式。Anthropic 的服務可以暫時保留對話，讓應用程式在後續請求中只傳送最新訊息。

它的吸引力很直觀。隨着對話變長，每次來回攜帶完整交流，意味重複傳送愈來愈多內容。Anthropic 表示，Message Threads 可以縮小後續請求，並縮短*首個詞元時間*，也就是回答開始出現之前的等候時間。本次研究審閱的發佈資料只對這些好處作了定性描述；它們在日常使用中的實際幅度仍有待測量。

這項功能同時帶來一個走得很快的時鐘。Anthropic 的文件寫明，保存的對話會在最後一次請求五分鐘後過期。一次停頓，就可能改變應用程式下一步要做的事。

那麼，用戶在五分鐘後回來，會發生甚麼事？

可以想像把一疊工作文件留在圖書館書桌上。文件還在桌上時，你只需帶一張新紙回來便可繼續閱讀；桌面清空後，你就要重新帶來完整文件夾。在這個比喻中，Anthropic 提供書桌，應用程式仍負責保管文件夾。

這項分工正是 Message Threads 的核心，也是一個小型本機實驗為何要刻意等待六分鐘再繼續。

功能從一個名為 `create` 的請求開始。應用程式傳送完整對話，服務回傳一則帶有識別資料的回應。下一輪可以使用 `continue`，把新訊息與上一則回應 ID 一起傳送。這個引用告訴服務應該使用哪一段較早的對話。

Anthropic 的文件列出 Claude API，也就是應用程式與 Claude 通訊的介面；同時亦涵蓋 Amazon Bedrock、Google Cloud 的 Vertex AI 和 Microsoft Foundry。開發者也可以透過這些雲端平台存取模型。

在這套機制中，保留的對話被稱為「盡力而為」的暫存狀態。最後一次請求五分鐘後，對話串會過期。Anthropic 另行說明，相關資料會在最後一次使用後一小時內刪除。這是兩條不同的界線：一條關乎對話串能否繼續使用，另一條關乎保留資料何時刪除。

繼續請求可能收到 HTTP 404，表示所請求的資源目前無法使用，同時帶有 `thread_not_found` 錯誤碼。過期是文件列出的一種原因；地區可用性問題，以及被引用的對話串失敗或已被刪除，也可能產生同一錯誤。

Anthropic 的復原方法與圖書館比喻完全一致：把文件夾帶回來。應用程式建立一條新對話串，並重新傳送完整對話。

為了檢查這種復原方式，本次研究採用一個刻意保持簡單的本機模擬。一個假的對話串服務代替遙距服務，由客戶端程式處理對話。整個實驗都在本機運行，Anthropic API 呼叫次數為零，服務供應商費用也為零。它關注的是暫存狀態過期時客戶端的行為。

運行開始前，測試先凍結了規則。假服務會保留對話串狀態 300 秒，也就是五分鐘。客戶端分兩次提交數字 17 和 5，中間刻意停頓。成功條件包括：最終驗收值為 22，剛好發生一次復原，用戶訊息 ID 沒有重複，啟動後也沒有人工介入。

簡單的加法讓復原結果很容易檢查。真正關鍵的工作，是在故障前後完整保住對話。

客戶端先為包含 17 的那一輪建立對話串，然後等待 360 秒，也就是現實時間中的六分鐘。這段停頓超過了假服務設定的五分鐘壽命。

接下來是包含 5 的一輪。客戶端嘗試延續原有對話串，收到注入的過期錯誤。隨後，它取出自己的完整帳本，也就是按次序保存的對話紀錄，並透過新的 `create` 請求重新傳送這段歷史。

運行最終得到驗收值 22。紀錄中有一次復原，重複用戶訊息 ID 為零。本機請求一共三次：首次建立成功、延續請求失敗，以及使用重播歷史再次建立成功。整個過程耗時 360.104 秒，其中幾乎全部時間來自刻意設定的六分鐘等候。

對於這個特定客戶端和這次注入的故障，復原成功了。

這個結果的範圍很重要。實驗使用的是行為遵循固定規則的確定性假服務。它提供了具體證據：客戶端能夠保留帳本、遇上預定的過期事件，並成功重播對話。真實 Claude 的回應速度、計費影響、模型行為和服務儲存時序，仍需要在實際平台上測量。

通過驗收的答案也只屬於一道定義嚴格的加法題。它證明本機復原符合測試預先設定的條件。要了解智能體在真實工作日中的協助質素，還需要來自那些任務本身的證據。

Anthropic 提供一個 TypeScript SDK 輔助元件，也就是可以直接使用的程式模組，代為處理大量對話紀錄工作。文件說明，該元件保留歷史，並在第一輪之後只傳送新訊息。它還會針對三類錯誤自動重播一次：對話串無法使用、對話串已經延續，以及延續請求仍在進行。

這項便利也有清楚界線。輔助元件的歷史只存在於正在運行的程序記憶體中。程序一旦結束，復原便依賴應用程式自己維護的持久對話紀錄，例如保存在能夠跨重啟留存的儲存系統內。

重播對話還會產生另一次模型請求。應用程式若連接着現實世界的動作，就會遇到另一個問題：它如何分辨某項動作已經完成，還是仍在等候執行？

以能夠建立預訂的應用程式為例，復原後的對話可能包含較早的預訂請求。周邊軟件需要有自己的方法識別已經完成的預訂，並控制後續嘗試。這說明了另一項獨立責任：防止重複動作的保護機制，應與對話復原並存。本機加法實驗測試了對話路徑；預訂系統和其他外部工具需要符合各自影響範圍的檢查。

因此，Message Threads 改變的是正常交流期間應用程式需要傳送多少歷史。要讓交流可以重建，紀錄仍由應用程式掌握。

六分鐘的停頓把這項安排變得具體可見。服務可以暫時替應用程式保管桌上的文件；當暫存對話串過期時，讓交流繼續下去的是應用程式自己的文件夾。
