# Claude 的临时记忆过期后会发生什么

与 AI 助手对话时，交流看起来是连续的。你提出问题，读完回答，再补充一个细节。支撑这段交流的软件必须把足够的前文交给模型，它才能理解每一条新消息。在普通实现里，对话越长，应用就越需要重复发送早先的消息。

重复传送这些内容，是智能体应用承担的工作之一。应用位于用户与模型之间：它收集消息、保存对话记录并准备请求。使用工具的应用还可能安排查询资料、修改记录等动作。Anthropic 的 AI 模型 Claude 则根据应用提供的上下文生成回答。

2026 年 11 月 2 日，Anthropic 宣布推出一项名为 **Message Threads** 的测试功能，改变了应用传送上下文的方式。Anthropic 的服务可以暂时保留对话，让应用在后续请求中只发送最新消息。

它的吸引力很直观。随着对话变长，每次来回携带完整交流意味着重复传送越来越多的内容。Anthropic 表示，Message Threads 可以缩小后续请求，并缩短*首个词元时间*，也就是回答开始出现之前的等待时间。本次研究审阅的发布资料只对这些好处作了定性描述；它们在日常使用中的实际幅度仍需要测量。

这项功能同时带来一只走得很快的时钟。Anthropic 的文档写明，保存的对话会在最后一次请求五分钟后过期。一次停顿，就可能改变应用下一步要做的事。

那么，用户在五分钟后回来，会发生什么？

可以想象把一叠工作资料留在图书馆书桌上。资料还在桌上时，你只需带一张新纸回来就能继续阅读；桌面清空后，你就要重新带来完整文件夹。在这个比喻中，Anthropic 提供书桌，应用仍负责保管文件夹。

这项分工正是 Message Threads 的核心，也是一个小型本地实验为什么要有意等待六分钟再继续。

功能从一个名为 `create` 的请求开始。应用发送完整对话，服务返回一条带有识别信息的响应。下一轮可以使用 `continue`，把新消息与上一条响应 ID 一起发送。这个引用告诉服务应当使用哪一段早先的对话。

Anthropic 的文档列出 Claude API，也就是应用与 Claude 通讯的接口；同时还涵盖 Amazon Bedrock、Google Cloud 的 Vertex AI 和 Microsoft Foundry。开发者也可以通过这些云平台访问模型。

在这套机制里，保留的对话被称为“尽力而为”的临时状态。最后一次请求五分钟后，对话串会过期。Anthropic 另行说明，相关数据会在最后一次使用后一小时内删除。这是两条不同的边界：一条关乎对话串还能否继续使用，另一条关乎保留数据何时删除。

继续请求可能收到 HTTP 404，表示所请求的资源当前不可用，同时带有 `thread_not_found` 错误码。过期是文档列出的一种原因；区域可用性问题，以及被引用的对话串失败或已经删除，也可能产生同一错误。

Anthropic 的恢复方法与图书馆比喻完全一致：把文件夹带回来。应用建立一条新对话串，并重新发送完整对话。

为了检查这种恢复方式，本次研究采用了一个刻意保持简单的本地模拟。一个假的对话串服务代替远程服务，由客户端程序处理对话。整个实验都在本地运行，Anthropic API 调用次数为零，服务商费用也为零。它关注的是临时状态过期时客户端的行为。

运行开始前，测试先冻结了规则。假服务会保留对话串状态 300 秒，也就是五分钟。客户端分两次提交数字 17 和 5，中间有意停顿。成功条件包括：最终验收值为 22，恰好发生一次恢复，用户消息 ID 没有重复，启动后也没有人工介入。

简单的加法让恢复结果很容易检查。真正关键的工作，是在故障前后完整保住对话。

客户端先为包含 17 的那一轮建立对话串，然后等待 360 秒，也就是现实时间中的六分钟。这段停顿超过了假服务设定的五分钟寿命。

接下来是包含 5 的一轮。客户端尝试延续原有对话串，收到注入的过期错误。随后，它取出自己的完整账本，也就是按顺序保存的对话记录，并通过新的 `create` 请求重新发送这段历史。

运行最终得到验收值 22。记录中有一次恢复，重复用户消息 ID 为零。本地请求一共三次：首次建立成功，延续请求失败，使用重放历史再次建立成功。整个过程耗时 360.104 秒，其中几乎全部时间来自有意设置的六分钟等待。

对于这个特定客户端和这次注入的故障，恢复成功了。

这个结果的范围很重要。实验使用的是行为遵循固定规则的确定性假服务。它提供了具体证据：客户端能够保留账本、遇到预定的过期事件，并成功重放对话。真实 Claude 的响应速度、计费影响、模型行为和服务存储时序，仍需要在实际平台上测量。

通过验收的答案也只属于一道定义严格的加法题。它证明本地恢复满足了测试预先设定的条件。要了解智能体在真实工作日中的协助质量，还需要来自那些任务本身的证据。

Anthropic 提供一个 TypeScript SDK 辅助组件，也就是能够直接使用的程序模块，代为处理大量对话记录工作。文档说明，该组件保留历史，并在第一轮之后只发送新消息。它还会针对三类错误自动重放一次：对话串不可用、对话串已经延续，以及延续请求仍在进行。

这项便利也有清楚边界。辅助组件的历史只存在于正在运行的进程内存中。进程一旦结束，恢复就依赖应用自己维护的持久对话记录，例如保存在能够跨重启留存的存储系统里。

重放对话还会产生另一次模型请求。应用若连接着现实世界的动作，就会遇到另一个问题：它如何分辨某项动作已经完成，还是仍在等待执行？

以能够创建预订的应用为例，恢复后的对话可能包含早先的预订请求。周边软件需要有自己的办法识别已经完成的预订，并控制后续尝试。这说明了另一项独立责任：防止重复动作的保护机制，应当与对话恢复并存。本地加法实验测试了对话路径；预订系统和其他外部工具需要符合各自影响范围的检查。

因此，Message Threads 改变的是正常交流期间应用需要传送多少历史。要让交流可以重建，记录仍由应用掌握。

六分钟的停顿把这项安排变得具体可见。服务可以暂时替应用保管桌上的资料；当临时对话串过期时，让交流继续下去的是应用自己的文件夹。
