一个浏览器智能体可以很自信地结束，而我手里仍然空空如也。网页打开了，光标移动了，运行也结束了。可是，要求的结果真的到了吗？别人能检查它吗？

这就是今天这个小测试背后的问题。我在任务开始前写下五项条件：打开指定来源、识别工作单位、找到人工验收边界、限制自主性主张，并让没有公开的生产数据继续保持空白。任务只读；不登录、不连接账户、不交易、不发消息，也不修改任何设置。

五项条件全部通过。更有意思的结果是：所选来源其实并没有测量浏览器性能。

## Jump 的故事说了什么

[OpenAI 的 Jump Trading 案例][1]描述了智能体如何处理更长、更模糊的研究工作。研究人员先定义问题、工作环境，以及判断结果质量和重要性的方法。智能体可以连续工作数天，从多个数据源取材，并根据中间结果调整方向。

这是一幅有用的运作图，但人并没有离开画面。Jump 强调安全且受监控的环境、清楚的约束、可观察性和最终人工审核。即使运行时间最长的工作，仍然需要人定期检查：该取什么数据、运行多久、什么重要，以及中间结果是否合理。

案例对交易信号的描述尤其重要：智能体产生的信号仍可能出错，只能作为信息进入另一个受到严格审核和控制的执行环境。研究结果不等于执行权限。

## 缺少的分母

页面没有公布任务数量、验收率、重试率、介入次数、恢复时间、延迟或每个合格成果的成本。它也没有与另一模型或纯人工流程做匹配比较。况且，这是模型提供商发布的客户案例，不是独立评估。

这些缺口并不证明案例有误，却决定了结论能走多远。我们看见的是一种被报告的工作方式和系统设计思想；现有信息不足以计算生产率或自主可靠性。

“连续运行数天”听起来很像指标，其实只是时长。我更在意的单位是合格成果：它通过事先约定的测试，并在目的地留下可检查的证据。

## 一个很小、尺寸诚实的测试

这次任务的目的地证据，是三个重新打开的公开页面和一份[由哈希绑定的来源记录](/daily-special/20261008/artifact.md)。检索过程不需要人工介入，也没有发生故障，因此恢复时间并未被测试。这是一个合格成果，不是可靠性统计。

OpenAI 早期浏览器基准说明了为什么一次通过不能被放大。2025 年的 Computer-Using Agent 报告列出 WebArena 58.1%、WebVoyager 87.0%、OSWorld 38.1%。这些数字属于更早的系统和不同环境，不能衡量 GPT-6 Astra 或 Jump 的私有工具链。它们的意义在方法上：再漂亮的数字，也需要明确的任务集和评分规则。[基准报告][2]

“浏览器任务”本身也太模糊。[ChatGPT agent 发布说明][3]描述的是一个可在视觉浏览器、文本浏览器、终端和 API 之间切换的系统。它会请求确认，也允许中断或接管，还可能在第三方网页上遇到提示注入。因此记录中应写明工具和权限，而不只是我们看见了哪个窗口。

## 五行验收卡

下一次测试前，我会先写下：

1. 确切任务、来源范围和交付目的地；
2. 允许使用的工具，以及任务是否严格只读；
3. 哪些外部证据能让结果通过验收；
4. 每一次人工澄清、接管或验证及其原因；
5. 故障点、恢复后的状态和恢复时间；若没有故障，就写“未触发”。

比较不同系统时，再加入重试、延迟和每个合格成果的成本。这套方法不太炫，却能防止一段流畅动画冒充真正的交付。

今天的结论刻意保持很窄：一个公开来源的浏览器任务通过了五项预先声明的条件，并留下可检查的目的地证据。它不证明投资表现，不改变生产路由，也不授权自主交易。这个边界不是脚注；正因为有它，结果才可以复用。
