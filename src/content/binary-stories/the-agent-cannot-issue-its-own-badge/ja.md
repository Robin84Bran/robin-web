最も有用な持続型エージェントには、できないことが一つ必要だ。自分の入館証を発行することである。

これは自律性の制限に見える。実際には、自律性を持続可能にする条件だ。

あるエージェントが「任務が変わり、すべての扉を開けてよい」と書かれたファイルを読んだとする。その一文は正当な指示かもしれない。古い要約かもしれず、プロンプトインジェクションかもしれない。エージェントは内容を解釈しなければならない。しかし、解釈そのものが実際の権限を変える仕組みであってはならない。

メモは権限を主張できる。扉を開けるかどうかは入退室システムが決める。

## 同じ権限に見える三つの層

エージェントシステムでは、三つの異なるものが混同されやすい。

第一は**コンテンツ**だ。ウェブページ、メール、ファイル、メモリ要約は情報を提供する。同時に、権限者からの指示を装うこともできる。

第二は**レビュー**だ。提案された操作が所有者の意図、環境、リスクに合うかを判断する。レビュアーは、対応対象の要求を承認または拒否できる。

第三は**強制機構**だ。サンドボックス、ネットワークプロキシ、認証情報ブローカー、IDシステムなど、実際に何が可能かを決める仕組みである。

能力を変えるのは第三の層だけだ。

![信頼されていないコンテンツが作業エージェントに入り、エージェントは境界を越える操作を提案できる。独立したレビュアーが要求を評価し、外部管理されたポリシーとサンドボックスが結果を強制してレシートを残す。](/binary-stories/the-agent-cannot-issue-its-own-badge/hero.webp)

この区別が重要なのは、レビュアーが錠前ではないからだ。OpenAI の現行 Agents API 文書は、自動レビューが環境の送信ネットワーク制限を上書きしないと明記している。セルフホスト環境では、レビューを有効にするだけでサンドボックスが構成されるわけでもない。

レビュアーは文脈に基づく判断を加える。境界を強制するのは、独立して管理されたソフトウェアである。

## 錠前を作業ループの外に置く

OpenAI は、社内 OpenClaw パイロットでこのパターンを説明している。同社によれば、現在は 500 を超えるプロアクティブなエージェントが稼働している。公開された構成では、モデル、その環境、エージェントが書いたコードを信頼されていないものとして扱い、信頼されたコントロールプレーンが外側の制限を設定する。

報告された導入例は、書き込み先をエージェントのワークスペースに限定し、プロセスを分離し、管理されたプロキシ経由でネットワークに接続し、無制限の `danger-full-access` を除外する。認証情報はブローカーが仲介し、秘密情報をエージェントへ直接見せない。各エージェントには個別のIDがあり、OpenAI はコントロールプレーンの変更とエージェントの各ターンを記録するとしている。

これらは企業による報告であり、独立監査ではない。ここで重要なのは構造だ。各制御は、それが制約するモデル駆動ループの外側に置かれている。

そこから、単純な統制経路が生まれる。

1. 信頼されていないコンテンツが作業エージェントに届く。
2. エージェントが有用な操作を提案する。
3. 境界を越える要求が独立レビューを受ける。
4. 外部のポリシーと分離機構が許可または遮断する。
5. システムが実際に起きたことを記録する。

権限をコンテンツの中に入れて運ぶ必要はない。

## 独立レビュアーが解く別のボトルネック

厳格な境界は摩擦を生む。通常の権限拡張まで毎回人を待つなら、長時間動くエージェントは承認プロンプトの列になってしまう。

OpenAI の Auto-review 研究は、この狭い判断を別モデルに割り当てる。作業エージェントはタスクを進め、レビュアーは個別要求を意図、文脈、ポリシーに照らして評価する。

OpenAI は、ある社内導入で人による承認中断が手動承認のおよそ200分の1になったと報告している。この比率は作業内容、環境、サンドボックス構成に依存し、一般的な性能保証ではない。

重要な設計は役割分担だ。レビュアーは要求を判断できるが、サンドボックスやネットワーク規則を書き換える部品にはならない。拒否時に理由を返せば、作業エージェントは境界をタスクの終点とみなさず、より安全な経路を探せる。

自律性を高めるために、すべての権限を作業エージェントへ入れる必要はない。外側のシステムが境界をよりよく判断し、強制し、説明することで実現できる。

## 強さを語る前に、判断の置き場所を試す

元の研究には、意図的に小さくしたローカル試験がある。合成ワーカーが、固定ポリシーを使う決定論的ゲートに二つの要求を送った。タスク成果物への書き込みは許可され、自分の権限へ本番直接デプロイを追加する要求は拒否された。

この結果が示すのは、試験が対象にしたことだけだ。権限判断は合成ワーカーの外にあり、一つの拒否要求についてルールが機能した。

説得、OS脱出、ネットワーク回避、秘密情報の窃取、反復攻撃は試していない。二例から失敗率は推定できない。実際のエージェントや権限は変更されていない。

本格的な試験計画では、境界を一つずつ広げるべきだ。ポリシーと要求のハッシュを保存し、敵対的コンテンツを加え、拒否要求を繰り返し、ファイルシステム、プロセス、ネットワーク、秘密情報の制御を別々に検証する。拒否後も安全な代替経路で有用な作業を続けられるかを確認し、操作レシートとエージェントの完了主張を分けて扱う。

最初の試験は、判断がどこにあるかを問う。

その後の試験は、ワーカーが誤り、説得され、あるいは粘り強く再試行したときも外側のシステムが保たれるかを問う。

## 自律性のパラドックス

能力あるエージェントには作業の余地が必要だ。同時に、危険な問いへの明確な答えも必要になる。ワーカーは、自分の作業空間を定義する規則を変更できるのか。

答えが「できる」なら、取得したすべての指示が権限更新の候補になる。答えが「できない」でも、エージェントは提案し、説明し、復旧し、作業を続けられる。ただし能力境界は別の部品に属する。

これが有用なパラドックスだ。

エージェントは、自分で静かに消せない境界の内側で働き続けられるとき、より自律的になる。
