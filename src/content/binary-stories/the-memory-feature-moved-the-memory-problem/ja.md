記憶機能は、記憶の問題を移しただけだ。

Anthropic は2026年11月2日、Message Threads のベータ版を公開した。クライアントはスレッド作成時に会話全体を送り、その後は新しいメッセージと直前のレスポンス ID だけを送れる。スレッドが利用できる間は、毎回すべての文脈を運ぶ必要がない。

これは有用だ。しかし、アプリケーションの永続記憶ではない。

サーバー側スレッドは短命な作業コピーだ。Anthropic の文書では、最後のリクエストから5分で利用期限を迎え、保持データは最終利用から1時間以内に削除される。スレッドが失われた場合、アプリケーションは会話全体から新しいスレッドを作る。つまり、近道は自分より長く残る台帳に依存している。

## 二つのコピー、二つの役割

サーバー側のコピーは正常系を高速化する。最初に履歴全体を受け取り、スレッド ID が有効な間は差分だけを受け取る。

アプリケーション側のコピーは障害系を担う。順序付きのユーザー、アシスタント、ツールのメッセージを保存し、スレッドの期限切れ、一時的な利用不能、プロセス消失の後でも会話を再構築できるようにする。

![一時的な5分間のサーバースレッドが正常系を速め、永続的なアプリケーション台帳が再生と復旧を担う。](/binary-stories/the-memory-feature-moved-the-memory-problem/hero.webp)

この分担は好みではなく、復旧契約から導かれる。`thread_not_found` は、失われたスレッドの中にしかない履歴を復元できない。復旧は新しいスレッドを作り、アプリケーションが保存した完全な記録を再生することから始まる。

TypeScript SDK のヘルパーは、実行中プロセスに会話履歴を保持し、初回以降は新しいメッセージだけを送る。だが、プロセスメモリも境界だ。クラッシュ、再起動、別プロセスへの引き継ぎを越えて復旧するには、その外側に永続的な情報源が必要になる。

スレッド ID を永続記憶として扱うと、設計は逆転する。交換可能な参照が真実の源になり、復旧できる唯一のコピーが消失可能になる。

## 期限切れは差分を完全再生に戻す

最小の仕組みは六つの手順で表せる。

1. 完全で順序付きの会話をアプリケーション台帳へ永続化する。
2. その履歴全体からサーバースレッドを作る。
3. スレッド ID とレスポンス ID を交換可能な状態として保存する。
4. スレッドが有効な間は新しいターンだけを送る。
5. `thread_not_found` を受けたら、完全な台帳から新しいスレッドを作る。
6. 新しいレスポンス ID から継続し、同じユーザーターンを重複させない。

重要なのは手順5だ。差分プロトコルが成立するのは、双方が同じ過去状態を共有している間だけである。サーバー側コピーが消えれば、クライアントは自分の記録から共有状態を作り直さなければならない。

したがって「スレッドが5分」ということは、「会話が5分」という意味ではない。再構築に必要な状態をアプリケーションが持っていれば、会話は複数のスレッド寿命をまたげる。

## 一度のローカル障害注入

元の Special は、決定論的で認証情報を使わない模擬サービスにより復旧形状をテストした。スレッド寿命は300秒、クライアントは360秒停止し、次のリクエストを意図的に期限切れの外側へ置いた。

観測結果は限定的で明確だった。最初のターンは17、復旧後のターンは5を加えて22を返した。再生は一度、重複したユーザーターンはゼロ、プロバイダー API 呼び出しもゼロだった。

これは、ローカルクライアントが一度の期限切れから会話ターンを重複させずに復旧したことだけを示す。実際の Claude における遅延、リクエスト量削減、token、課金、モデル品質、保存挙動は示していない。代表的な実運用ループで測るまで、これらは **UNKNOWN** のままだ。

Anthropic のリリースノートは、後続リクエストの縮小と最初の token までの時間短縮を定性的に述べている。これは仕組みを支持するが、普遍的な節約を証明しない。測るべき値は正常系一回の送信量だけではなく、通常ターン、期限切れ、プロセス消失、復旧を通じて受理された作業のコストと信頼性である。

## 会話の復旧は、外部作用の復旧ではない

エージェントは言葉を再構築できても、動作を重複させることがある。

期限切れ直前のターンが、チケット作成、指示送信、外部記録更新をツールへ依頼したとする。外部システムが処理を受理した後、確認レスポンスだけが失われた場合、会話を再生しても「作用はすでに起きたか」という問いには答えられない。

そのためには別の作用台帳が必要だ。各外部動作について、冪等キーまたは action ID、試行した要求、観測した受理レシート、そして `ACCEPTED`、`NOT_ACCEPTED`、`UNKNOWN` を区別するための読み戻しを保存する。

役割は四層に分かれる。

- **会話台帳**は文脈を再構築する。
- **スレッド参照**は現在のリモートセッションを高速化する。
- **作用台帳**は完了済み動作の暗黙的な再実行を防ぐ。
- **読み戻し**は復旧完了を宣言する前に宛先の結果を確認する。

ローカル期限切れテストが扱ったのは会話復旧だけで、外部作用はなかった。したがって、本番での重複排除は依然 **UNKNOWN** であり、スレッド機能が自動的に解決したとは言えない。

## 最小の復旧可能設計

復旧可能なシステムに巨大な「記憶基盤」は必須ではない。ただし、状態の所有者は明確でなければならない。リモート参照に依存する前に会話イベントを永続化する。スレッド ID とレスポンス ID は交換可能なキャッシュキーとして扱う。再生を決定論的かつ観測可能にする。外部作用には独立した冪等性とレシートを持たせる。正常系だけでなく、期限切れとプロセス再起動をテストする。実運用の経済性を測る前に、定性的な利点を本番の事実へ昇格させない。

スレッドの価値は、短命で軽量でいられることにある。アプリケーション台帳の価値は、自分を性能上の近道だと偽らないことにある。

スレッドを近道として使い、台帳を真実として扱う。
